Pattern 2

Access Control with Metadata Filters

Tag documents with access control attributes (department, role, tenant ID), then filter at retrieval time so users only see documents they're authorized to access.

Sidecar Format

{
  "metadataAttributes": {
    "department": {
      "value": {
        "type": "STRING",
        "stringValue": "engineering"
      }
    },
    "access_level": {
      "value": {
        "type": "STRING",
        "stringValue": "internal"
      }
    }
  }
}

Use Cases

  • ✓ Multi-department chatbot (HR, eng, security)
  • ✓ Multi-tenant SaaS (filter by tenant_id)
  • ✓ Healthcare (patient_id per doctor)
  • ✓ Compliance (classification levels)

Access Control Filter — Department Scoping

# Filter injected by app based on authenticated user's department
authenticated_dept = jwt_claims["custom:department"]

response = dp.retrieve(
    knowledgeBaseId=kb_id,
    retrievalQuery={"text": user_query},
    retrievalConfiguration={
        "managedSearchConfiguration": {
            "numberOfResults": 5,
            "filter": {
                "equals": {"key": "department", "value": authenticated_dept}
            }
        }
    }
)

Cross-Department Access — IN Filter

# User with access to multiple departments
user_depts = ["engineering", "security"]

"filter": {
    "in": {"key": "department", "value": user_depts}
}

Strengths

  • ✓ No KB or data source changes needed
  • ✓ Works with any auth system
  • ✓ Flexible multi-attribute filtering
  • ✓ Low latency — filtering in vector store

Limitations

  • ✗ Caller knows the KB ID
  • ✗ App must enforce filter injection
  • ✗ No server-side enforcement
  • ✗ Bypassing the app = sees everything

🎯 When to Use

Your application controls access and can reliably inject the correct filter for each authenticated user. Works well when combined with Cognito, SSO, or any identity provider that provides user attributes. For server-side enforcement, add a Gateway (Pattern 3+).
